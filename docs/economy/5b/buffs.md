# Phase 5B · Buffs and Double Cash

**Status: proposal only.** Nothing here is live. No `src/` file, catalog row or player document changes until you approve.

- **Framework 5b.4.** Every table in this document is **generated**. `node scripts/economy/5b/render-docs.js` fills each block from `scripts/economy/5b/buffs.js` `markdownTables()` at the current framework version, and each block ends with its provenance line (version and shared digest). Prose cites numbers only by pointing at a table. `check-shared.js` fails if a table is stale.
- **One model.** The buff layer is a *system* on the shared lifecycle core (`lifecycle.js`). `integrate.js` composes it with rods, world, quests and streak into the reference loop, and every lifecycle figure here comes from `integrate.run()`. The module has no time-stepping loop of its own. `lifecycle(archetype)` is a traced `integrate.run()`: the trace records the exact ledgers at every day boundary and one row per played day, and changes no number (check `trace-is-observational`). Static figures (box buff odds, Lucky Draw crate chains, one buff's value at a stage, today's catalog) come from the framework's pure functions.
- **Counting rule.** A box's non-buff contents are valued once, by the system that grants it (quests: Daily Box; streak: Streak Crate and Chest). The buffs inside reach this system as `box` events and are valued here, once (check `buff-value-counted-once`).
- **Hand-set values:** only `PARAMS`. The shared buff rules (`F.BUFFS`: timing, duration, multipliers, Lucky Draw, stacking) and the event budget (`F.EVENTS`) are read from the framework. Every non-obvious choice is a proposed decision (§1), and `check-shared.js` checks each record against the value the model runs.
- **Finished-design inputs:** `streak.boxEV()` and `streak.boxDefinitions()` (buff odds per box), and the rods crate helpers `crateDefinition()`, `openOutcomes()`, `cratesDistribution()`, `cratePrice()`, `stageIncome()` and `assembly()`. These are crate helpers, not a gear source (R3).
- **Booster Packs** keep their exact contents and are valued nowhere (decision 12). A Lucky Draw charge is never spent on one.

**Governing rule:** *a buff multiplies play inside its window, never a stockpile built outside it.* Hoarding is not treated as an exploit; it simply stops mattering. Stored fish values never decay, so a player can keep fish and sell whenever they like. Saving *buffs* for a long session stays a legitimate choice, bounded at one window of the player's own income per buff (§5).

- **B3 is a live exploit, not a latent bug.** Only slash commands check expiry. An activated Double XP, Double Cash or Lucky Draw keeps applying on 'Fish again' casts, the catch-card Sell button and 'Open another' until the player's next slash command. Because of B2 the same unit can then be activated again, as often as the player likes. Anyone who holds one unit can use it this way today (bugs table, first row). How much it was used in production is not measured (§14, past use).
- **Deploy order** (`P-BUFFS-HOTFIX`, `P-BUFFS-FIX-DURATION`):
  - **B3 can ship now, alone.** Read-time expiry in the buff queries restores today's intended behaviour: a buff lasts the few seconds of B1 on every path. It changes no unit, catalog row or stored value.
  - **B1 and B2 ship together, and only in the deploy that stamps Double Cash at catch** (`P-DOUBLE-CASH`) and removes cash buffs from every sale path (the catch-card Sell button and `/sell`). Fixing the duration alone would make every buff permanent, because a used buff is never removed. Shipping B1 + B2 while sales still apply cash buffs would turn every held Double Cash into an hour of sale-time hoarding, which is the exploit decision 8 closes. The "today" rows of the frequency table (§4) size it for new players. Units that players already hold add to it, because the model starts from an empty stock.
  - **What the hotfix leaves open.** A `/sell` sent inside the few-second window still doubles the whole hoard, and B2 makes the unit reusable (bugs table, B3 evidence). It closes with B1 + B2 and `P-DOUBLE-CASH`. `P-BUFFS-HOTFIX` lists the alternatives that would close or limit it earlier, and what each costs.
- **What the live exploit changes elsewhere.** The switch to catch-time still needs no fish revaluation, because today's cash buffs are applied at sale and never stored on a fish. Units are still kept, because B2 never consumed one. Neither reason depends on buffs having had no effect. What past use does change is covered in §14.

## 4. Decision 8: Double Cash, sale-time or catch-time

The recommendation, catch-time, is the framework-level proposal `P-DOUBLE-CASH` in `decisions.js`. Catch-time is the buffs system itself (its ledger); every alternative is evaluated analytically on the same integrated run's daily rows (`doubleCashModels()`, `saleTimeHoarder()`), with the same buff arrivals.

<!-- generated:buffs-dc-models -->
| Model | Rule |
| --- | --- |
| **Catch-time (proposed)** | The buffs system itself: each Double Cash doubles the catch of the play its window covers (the session it starts, at each step's rates). |
| Catch-time, buff saver | Upper bound: the same units, each played for its whole hour (casual and regular players would have to play longer that day). |
| Catch-time, casts-based | Alternative duration: the buff lasts the next **400 casts** (one reference hour: `F.COOLDOWN` + `F.DESIGN_OVERHEAD_S`), however long that takes; mean-field on the daily rows. |
| Sale-time, sells every session | Sells what they catch, so the buff hour doubles that hour's sales: equals catch-time. |
| **Sale-time hoarder, uncapped** | Sells at x1 only the fish needed for the day's upkeep and progression purchases (gear, permits) beyond the non-fish cash it holds (quests, streak, salvage, Lucky Draw rebates); hoards the rest and sells it under the next Double Cash. Exact renewal DP over the day of the last hoard sale, P(arrival on a day) = 1 - e^(-lambda). |
| Sale-time hoarder, capped | The bonus per buff is capped at **1 h of the player's stage income** at the reference cadence; the hoarder sells exactly the capped amount under each buff. |

**Reading it.**
- **Uncapped sale-time makes hoarding the dominant strategy.** The hoarder's gain grows with buff frequency toward the hoardable share, far above everyone else's (frequency table). It needs no cap, no hoarding decision and no sale-time logic, and it matches every other sell modifier, which is already stamped at catch.

**Presentation** (the standing rule: public shows base, the account receives final).

## 14. Migrations (additive, idempotent)

1. **Clear stale activations:** `BuffData.updateMany({ active: true, endTime: { $lte: now } }, { $set: { active: false } })`, in the B1 + B2 deploy. Every existing activation passed its `endTime` a few seconds after it started (B1). Until the B3 hotfix it still applies on button paths; after the hotfix it applies nowhere, and this step only cleans up what `/boosters` displays. Counts are untouched: nobody loses a unit, because B2 never consumed one, so every unit a player ever received is still held. Re-running it matches nothing.
2. **Catalog text and fields:** `$set` description, `durationSeconds` and `charges` on the catalog buff rows by name, only where they differ.
3. **No player-document write** for `activeBuffs`: read-time default `{}`.
4. **No fish is rewritten or revalued.** Today's cash buffs are applied at sale and never stored on a fish, so fish caught before the deploy keep their stored values and are paid exactly those. Sales stop applying cash buffs in the same deploy as B1 + B2 (§2, deploy order). A buff that happens to be inside its few-second window at the deploy loses the rest of it; its unit is still held (B2).
5. **Legacy capabilities** (`['xp', …]`, `['cash', …]`, `['gacha', …]`) map to the proposed kinds at read time (`legacyKind`, `P-BUFFS-LEGACY`). No capability array is rewritten.

**Past use of buffs (facts and options; nothing is decided here).** Earlier versions of this document said no buff had ever had an effect. That was wrong (B3). Migrations 1, 4 and 5 still hold, for the reasons given in each step above. What changes is the reasoning behind keeping counts without a correction:
- **Units.** Every unit a player ever received is still held, including units already activated, because activation never consumed one (B2).
- **Effects.** Until the B3 hotfix ships, an activated buff applies on button paths until the player's next slash command (B3): Double XP on 'Fish again' casts, Double Cash on catch-card sales and Lucky Draw on 'Open another'. A `/sell` inside the few-second window doubles a whole hoard. Each unit can be activated again. Buffs arrive rarely today (headline table, "today"), and production has few accounts (`P-LEGACY-WEALTH`), but how often this happened is not measured.
- **Where the gains are now.** XP from a stale Double XP is in `xp`. Today's public (base) XP includes the buff (`modifiers.xpWithoutProfile`), so that XP is also in `publicXp` and the public level. Cash from a stale Double Cash is in balances. Both are carried like every other balance (`P-LEGACY-WEALTH`: nothing is wiped or clawed back).
- **How it could be measured (read-only, before approval).**
  - Cast journals list the buffs each cast read (`buffs`) and the XP multiplier. A cast that lists a buff more than a few seconds after that buff's last activation is a button-path use. Only the last activation can be recovered (`endTime` minus the window), because `endTime` is overwritten on each activation.
  - GachaOpen journals list buff sources.
  - Button sales and `/sell` record no multiplier. A Double Cash listed on a cast journal shows that a chain was live, not what was sold under it.
  - A BuffData stack with an `endTime` was activated at least once.
  - Where analytics are enabled, Interaction records show `/equip` and the button clicks that followed it.
- **After B1 + B2**, each held unit becomes one real hour of the proposed buff, whether or not it was used before (value per buff table, §5).
- **Compensation for the switch to catch-time.** A held Double Cash was meant to give a few seconds at sale; after B1 + B2 it gives a real hour at catch, so its intended value goes up. The switch removes only the unintended uses: button chains, and a hoard sold inside the window. No compensation is proposed, and that reasoning does not depend on buffs having had no effect.

The options, each a decision for you (`P-BUFFS-LEGACY` records the proposal and these alternatives):
- **keep counts, no clawback** (proposed): additive and idempotent. Players who used a unit on button paths keep both the gains and the unit.
- **consume one unit from every stack that was ever activated:** a stand-in for past use. It rewrites counts, and it also takes a unit from players who only had the few-second window.
- **size past use first** from the journals above, then choose.
- **claw back XP or cash gained from stale buffs:** not proposed. It conflicts with the standing constraint that `P-LEGACY-WEALTH` records (never wipe user or progression data).

## 16. Risks and open issues

- **The button-path exploit is live until the B3 hotfix ships** (§2; bugs table). It needs one held unit and an ordinary click sequence, and B2 makes the unit reusable.
- **Shipping B1 without B2** turns every buff into a permanent one. Test 2 guards it.
- **Shipping B1 + B2 before `P-DOUBLE-CASH`** turns every held Double Cash into an hour of sale-time hoarding (frequency table, "today" rows, plus the units players already hold). `PARAMS.rollout` and test 4 keep them in one deploy.
- **Open issue: the 30-day cash-share targets** (`PARAMS.targets.cashShareMax30d`) fail for casual, regular and active players on the integrated 5b.4 model (cash-share checks table below; income share table). The Double Cash part is inside every target; the excess is the Lucky Draw assembly rebate, which on the rods path lands on the early T1/T2 assemblies and, for the casual player, is measured against a fishing income that is small next to their quest and streak cash. No parameter was changed. The options, each a decision for you:
  - accept it: the rebate is progression spending avoided, lumpy by design, and the XP and R2 checks all pass;
  - measure the target on all cash income or on Double Cash only (the income share table has both views);
  - a smaller Lucky Draw (K = 1, Lucky Draw K table), or no Lucky Draw from events. The with/without-events table shows that dropping the event budget alone does not bring the casual player under the target on fishing income.
- **Wall-clock UX.** A player who activates and then gets interrupted loses the rest of the hour. Mitigations: an explicit confirmation, the remaining time on the catch card and in `/boosters`, and the queue (activate the next one when you have time). Casts-based durations avoid this but reward barely fishing (duration table), so they are not proposed.
- **Event budget discipline.** The event lever is the only source that can move the buff share materially. The budget should be enforced in code as a per-player cap per 30 days, not left to scheduling.
- **Lucky Draw semantics change for held items.** Existing Lucky Draws become bonus-slot charges, which is better on every crate. The effect differs from the old description, so the new text must ship with it.
- **The Lucky Draw value depends on the rods crate design.** `luckyAssembly()` mirrors `rods.cratesDistribution()`'s chain to evaluate lucky opens; the mirror is checked exact (`lucky-chain-reproduces-rods`), but a `rods.cratesDistribution(t, { def })` override would leave one implementation.
- **Model limits.** Expected values with Poisson arrivals: an individual player can go weeks without a buff. The model's player activates buffs rationally (`P-BUFFS-ACTIVATION`); an impatient one gets less. The capped sale-time variant is mean-field (exact once the hoard exceeds the cap) and is used only for the rejected alternative.
